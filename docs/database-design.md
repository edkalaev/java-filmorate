# Схема базы данных Filmorate

Структура реализована в [schema.sql](../src/main/resources/schema.sql) для H2.
При каждом запуске приложения таблицы удаляются вместе с данными и создаются
заново. После создания структуры [data.sql](../src/main/resources/data.sql)
заполняет справочники рейтингов MPA, жанров и статусов дружбы. Операторы
`CREATE TABLE` и `CREATE INDEX` содержат `IF NOT EXISTS`, а `MERGE` в `data.sql`
позволяет повторять заполнение справочников без дублирования записей.

## Таблицы и ключи

| Таблица | Назначение | Первичный ключ |
| --- | --- | --- |
| `users` | Пользователи | `id` |
| `films` | Фильмы; `mpa_id` ссылается на возрастной рейтинг | `id` |
| `mpa_ratings` | Названия и описания рейтингов MPA | `id` |
| `genres` | Коды и русские названия жанров | `id` |
| `film_genres` | Связь фильмов с жанрами | `(film_id, genre_id)` |
| `film_likes` | Лайки пользователей | `(film_id, user_id)` |
| `friendship_statuses` | Коды и названия статусов дружбы | `id` |
| `friendships` | Направленные связи пользователей со статусом | `(user_id, friend_id)` |

У фильма один необязательный рейтинг MPA и любое количество жанров.
Один жанр и один рейтинг могут относиться к нескольким фильмам.
Лайки связывают фильмы и пользователей по принципу «многие ко многим».
Каждая строка `friendships` ссылается на двух пользователей и один статус.

## Нормализация

1. В каждом столбце хранится одно значение. Жанры, лайки и друзья вынесены
   в отдельные строки таблиц связей, вместо массивов или вложенных объектов.
2. Атрибуты фильма и пользователя зависят от их `id`. В `friendships` статус
   определяется всей парой `(user_id, friend_id)`, поскольку у пользователя
   могут быть разные статусы связи с разными друзьями. У `film_genres` и
   `film_likes` нет неключевых атрибутов.
3. Название и описание рейтинга хранятся только в справочнике `mpa_ratings`.
   То же относится к названиям жанров и статусов. В таблицах сущностей и связей
   хранятся внешние ключи, поэтому нет зависимости вида
   `film_id → mpa_id → mpa_description` внутри одной таблицы.

Внешние ключи запрещают ссылки на несуществующие записи. Составные первичные
ключи запрещают повторный жанр, лайк или направленную связь дружбы.
Количество лайков и возраст пользователя вычисляются при необходимости.

## Значения справочников

Эти ID заданы в `data.sql`. Модели `Genre` и `Mpa` содержат `id` и `name`;
DAO загружают названия из БД, а фильмы хранят ссылки по ID. `genres.code`
остаётся внутренним кодом справочника. Статусы дружбы представлены enum
`FriendshipStatus`, связанным с БД через `friendship_statuses.code`.

| ID жанра | Код | Название |
| --- | --- | --- |
| 1 | `COMEDY` | Комедия |
| 2 | `DRAMA` | Драма |
| 3 | `ANIMATION` | Мультфильм |
| 4 | `THRILLER` | Триллер |
| 5 | `DOCUMENTARY` | Документальный |
| 6 | `ACTION` | Боевик |

| ID рейтинга | Название | Описание |
| --- | --- | --- |
| 1 | G | У фильма нет возрастных ограничений |
| 2 | PG | Детям рекомендуется смотреть фильм с родителями |
| 3 | PG-13 | Детям до 13 лет просмотр не желателен |
| 4 | R | Лицам до 17 лет просматривать фильм можно только в присутствии взрослого |
| 5 | NC-17 | Лицам до 18 лет просмотр запрещён |

| ID статуса | Код | Название |
| --- | --- | --- |
| 1 | `UNCONFIRMED` | Неподтверждённая |
| 2 | `CONFIRMED` | Подтверждённая |

## Дружба

Схема соответствует текущему `UserService`: неподтверждённая связь находится
в списке друзей отправителя, а встречное добавление подтверждает обе стороны.

Когда пользователь 1 добавляет пользователя 2, появляется одна строка:

| user_id | friend_id | status_id |
| --- | --- | --- |
| 1 | 2 | 1 |

Когда пользователь 2 добавляет пользователя 1, первая строка обновляется
и появляется обратная строка:

| user_id | friend_id | status_id |
| --- | --- | --- |
| 1 | 2 | 2 |
| 2 | 1 | 2 |

Повторный запрос не создаёт новых строк и не понижает подтверждённый статус.
Удаление дружбы убирает только исходящую строку пользователя. Если обратная
связь существует, она остаётся и становится неподтверждённой. Подтверждение
и удаление с изменением обратного статуса выполняются в одной транзакции.
PK, FK и CHECK не обеспечивают согласованность статусов
двух направлений: это правило реализует сервис при работе с БД.

## Примеры SQL-запросов

Параметры `:user_id`, `:other_user_id` и `:count` обозначают значения,
передаваемые через `NamedParameterJdbcTemplate`. Для обычного `JdbcTemplate`
их следует заменить на `?` и передать параметры в порядке использования.

### Все пользователи

```sql
SELECT id, email, login, name, birthday
FROM users
ORDER BY id;
```

### Все фильмы с рейтингом MPA

```sql
SELECT f.id, f.name, f.description, f.release_date, f.duration,
       f.mpa_id, m.name AS mpa_name, m.description AS mpa_description
FROM films AS f
LEFT JOIN mpa_ratings AS m ON m.id = f.mpa_id
ORDER BY f.id;
```

Жанры и лайки для коллекции фильмов можно получить отдельными запросами
и собрать в Java по `film_id`. Это сохраняет одну строку на фильм в основном
запросе и позволяет избежать отдельного запроса для каждого фильма.

```sql
SELECT fg.film_id, g.id AS genre_id, g.code, g.name
FROM film_genres AS fg
JOIN genres AS g ON g.id = fg.genre_id
ORDER BY fg.film_id, g.id;

SELECT film_id, user_id
FROM film_likes
ORDER BY film_id, user_id;
```

### Топ N популярных фильмов

```sql
SELECT f.id, f.name, f.description, f.release_date, f.duration, f.mpa_id,
       COALESCE(l.likes_count, 0) AS likes_count
FROM films AS f
LEFT JOIN (
    SELECT film_id, COUNT(*) AS likes_count
    FROM film_likes
    GROUP BY film_id
) AS l ON l.film_id = f.id
ORDER BY likes_count DESC, f.id ASC
LIMIT :count;
```

Фильмы без лайков тоже участвуют в результате. При равном количестве лайков
порядок задаётся ID фильма. Лайки подсчитываются до соединения с другими
таблицами, поэтому несколько жанров не увеличивают рейтинг фильма.
Параметр `count` должен быть неотрицательным.

### Список друзей пользователя со статусами

```sql
SELECT u.id, u.email, u.login, u.name, u.birthday,
       s.code AS friendship_status
FROM friendships AS fr
JOIN users AS u ON u.id = fr.friend_id
JOIN friendship_statuses AS s ON s.id = fr.status_id
WHERE fr.user_id = :user_id
ORDER BY u.id;
```

### Общие друзья двух пользователей

```sql
SELECT u.id, u.email, u.login, u.name, u.birthday
FROM friendships AS first_links
JOIN friendships AS second_links
  ON second_links.friend_id = first_links.friend_id
JOIN users AS u ON u.id = first_links.friend_id
WHERE first_links.user_id = :user_id
  AND second_links.user_id = :other_user_id
ORDER BY u.id;
```

Как и текущий сервис, этот запрос учитывает исходящие связи обоих статусов.
Для выдачи только взаимно подтверждённых общих друзей добавьте условия
`AND first_links.status_id = 2 AND second_links.status_id = 2`.

## Соответствие текущей валидации

`mpa_id`, `release_date` и `birthday` допускают `NULL`, поскольку сейчас
в моделях нет требования обязательности этих полей. Отсутствие жанров,
лайков или друзей означает отсутствие строк в соответствующей таблице связей.

Ограничения `duration > 0`, минимальная дата релиза, длина описания и запрет
дружбы с собой отражены в схеме. Проверка непустого названия, формата почты,
логина и даты рождения остаётся в приложении. Уникальность почты и логина
обеспечивается отдельными ограничениями `UNIQUE` для `users.email` и `users.login`.
